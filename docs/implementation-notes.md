# Implementation and verification

Latest release: **v0.29.1**. Sections below record development chronologically; the final release sections supersede earlier interaction and protocol notes.

Current version: **0.6.1**, targeting official Mindustry **v160.2**, source commit `89527f879b535b752376d9b935172be576320b59`. Compiled with its API jar and tested with its official server and desktop runtimes on Java 17.

## Interaction and layout

The 3×3 block uses `canControlSelect(Unit)` / `onControlSelect(Unit)` rather than `ControlBlock` possession. Native `InputHandler.buildingControlSelect` validates ownership/possession permission and invokes the callback on clients. The owning local client opens its editor while retaining its ship. Full proxy possession can despawn a core ship, so it is intentionally avoided. The regular `buildConfiguration(Table)` button is another local entry point and does not require the possession rule. Neither opening path authorizes Apply: the server validates again.

Native `consumePower(1f)` accounts for 60 power/second. Access requires a connected graph and full supply (0.999 tolerance). The dialog checks identity, tier, ownership, ship/building validity, enabled state, environment, power and distance while open. It stays open when Apply switches to another variant of the same tier. Stats are on the left, Cosmetics with Hull/Accents/Engine controls and a small live preview is in the center, controls are on the right, and the larger ship preview is below. The whole panel layout scrolls on smaller screens.

## Per-player speed and cargo

Native capacity, mining and building mechanics read UnitType fields. Three stable registered hulls (Alpha, Beta, Gamma) provide native content identity. `ShipVariant.view` shallow-clones a fully initialized hull using Object.clone, without calling a Content constructor. The view has the same ID/name, private primitive stat fields and an independent Stats object. No view enters the registered content sequence. Default settings use the vanilla type.

`UnitLoadouts` stores a small entry and cached view per customized unit. A reliable server-to-client packet carries world epoch, unit ID, tier, five bounded integer steps and three validated colour channels. Clients cannot submit this state to the server. A custom save chunk stores the same data for disk saves and initial/late-join world transfers. Native UnitEntity codecs carry the stable hull ID, so they alone are insufficient: the per-unit record is required. Trigger.update reattaches cached views after snapshots and before native Builder/Miner/Unit updates. It iterates tracked entries rather than scanning every unit each frame. Removed units are pruned; pending network entries wait for their unit; reset/world load clears transient state. Default entries also restore vanilla after stale snapshots.

Save headers now contain three hulls rather than 3,000 combinations. A fixed compatibility map of old names points to legacy views sharing the three stable IDs. The save-load event (or the first update for other world transfers) converts those views to tracked per-unit state; subsequent saves use the chunk. This compatibility map retains a fixed memory cost but adds no registered IDs/icons and never grows with future stat dimensions. A real v0.3.1 binary save is included as a migration fixture. The current colour-enabled saves require v0.6 or later; v0.4/v0.5 chunks remain readable with missing fields at their defaults.

`ShipVariant` is a v160.2 adapter. During `init`, after vanilla types have initialized, it borrows public, nonstatic UnitType fields from the base type, then derives speed, capacity, mining speed, build speed, build range and maximum HP on private views. Borrowing vanilla fields never copies Content identity. Cloning a stable hull deliberately preserves its own name/ID. During client `load`, after vanilla assets have loaded, it refreshes borrowed render fields. It reuses vanilla weapons, parts and engines as read-only references and skips the mutating UnitType init/load routines: rerunning them would duplicate engines or reinitialize shared weapons. It is hidden from selection/database UI and does not generate extra loadout icons. This reflection adapter is deliberately version-specific; revalidate it before upgrading the target game version or adding independently mutable weapon data.

Application changes the existing unit's type with `setType`, preserving its entity identity, controller, health, cargo and weapon mounts. It updates native team type counts and limits existing velocity to the new maximum. Other players' types and vanilla content are unchanged. Reducing capacity below the carried amount is rejected rather than deleting items.

Balance calculation is pure integer-step logic in `ShipLoadout`: each positive step costs 2, each negative step refunds 1; net spend is upgrade cost minus refunds, including negative balances. Available points are base budget minus net spend, so surplus manual refunds visibly increase available points. Speed factor is `1 + speedStep*0.10 - max(0,cargoStep)*0.05`; capacity is `round(baseCapacity*(1+cargoStep*0.20))`. The same step scales mining speed by `1 + cargoStep*0.15`; mining tier, range and hardness scaling are preserved. Construction multiplies base build speed by `1 + constructionStep*0.15` and base range by `1 + constructionStep*0.10`. The Fire Rate slider and positive Construction combine as `(1 + fireStep*0.10) * (1 - max(0,constructionStep)*0.08)`. Durability scales base maximum HP by `1 + durabilityStep*0.15` without changing armor. Negative cargo no longer grants an automatic speed bonus, and negative Construction does not boost weapons. Only explicit slider reductions affect point refunds. Server bounds and budgets are mandatory. The live preview compares loadout stats to the currently applied ship, not temporary status effects. Reset edits the draft; Apply confirms vanilla values.

## Construction fire rate hook

`ShipVariant.update(Unit)` multiplies only that unit's `reloadMultiplier` by its Construction factor. In the actual v160.2 generated unit update, native StatusComp recomputes/reset multipliers first, then UnitType.update runs, then Weapon.update consumes the multiplier. The hook is therefore recomputed once each native tick, composes with status effects, and does not accumulate. Both authority and clients derive it from the per-unit private view. Resetting to vanilla lets native updates restore the ordinary multiplier, including any unrelated status effects. Shared Weapon/BulletType data and ongoing mount state are never changed. This exact update order was checked in the release bytecode and verified through full engine updates and real clients; it is version-specific.

## Authority, persistence and restoration

The versioned custom packet `modular-shipyard-apply-v4` contains building position, expected current unit ID, five integer steps and three colour tokens. Native server packet dispatch supplies the actual sender. The server rejects mismatched current unit/controller, inaccessible/unpowered/enemy yard, unsupported ship, out-of-range or over-budget loadout, and unsafe capacity reductions. Payload length and parsing are bounded; per-player requests are throttled to one per 250ms. Responses go only to the sender. The UI waits for a response and provides an eight-second timeout message rather than assuming success. A reliable authoritative unit-state broadcast precedes the success reply; native snapshots carry only the stable hull ID.

The authority stores player UUID + tier entries in the data-directory file `modular-shipyard/loadouts-v1.properties`. It accepts existing two/three-column profiles with new controls at zero and writes updated entries as five columns. Unsupported field counts and invalid steps are ignored during restoration. It writes via a temporary sibling before replacement. A persistence failure rejects Apply before changing the unit. On `UnitChangeEvent`, a posted task rechecks the current player/unit, then restores the appropriate validated tier profile. A lower-tier ship never receives the higher-tier allocation. Unsupported/Erekir units and scorching worlds are excluded. Resetting the world clears transient requests, not saved preferences; disconnect removes rate-limit entries. Save format version is separate from the mod release version.

## v0.5.0 Durability and Fire Rate

The model has five independent integer steps. All share the same -4 through +5 limits, 2-point upgrade cost and 1-point reduction refund. Durability adds/subtracts 15% of base maximum HP per step; Fire Rate adds/subtracts 10% per step and multiplies Construction’s existing penalty. No additional automatic trade-off was added. Manual fire-rate reductions refund points; Construction’s automatic rate penalty still does not.

`UnitLoadouts.install` captures the authoritative health fraction, changes the private view/maxHealth, then restores that fraction against the new maximum. This handles full and damaged ships and prevents a repeated lower/raise cycle from healing them. `attach` during snapshot/save restoration never rescales health: native codecs already contain authoritative HP but temporarily resolve the neutral hull. Reattachment only restores its proper maxHealth. Weapon mounts, bullets, armor and vanilla type health remain unchanged. The existing per-unit reload multiplier hook handles Fire Rate together with Construction/status effects.

Apply/reply packets use v3, authoritative state packets use v2, and the custom chunk retains its stable name with payload version 2. The reader accepts payload versions 1 and 2, filling missing Durability/Fire Rate with zero for v0.4 saves. Player profiles accept 2, 3 or 5 fields; 4-field and malformed values are rejected. No content type IDs were added. Binary fixtures cover both v0.3.1 legacy-name migration and v0.4 per-unit chunk migration/resaving.

The UI uses five sliders, independent draft updates that retain all other slider values, live maximum-HP/final-rate comparisons and shared cost/refund accounting. Hull/Accents/Engine are the renamed placeholder colour tabs. The balance explanation sits below the panels, keeping the main controls and Apply/Reset compact. The whole layout still scrolls to reach rules and the ship preview.

## v0.6.0 functional colours

`ShipCosmetics` holds three immutable RGB24 values, with -1 meaning native defaults. The server validates all three; HEX parsing accepts exactly six digits, optionally `#`, and never accepts alpha. Cosmetics do not enter the points calculation. Default stats plus default colours still resolve to the vanilla type; cosmetic-only ships use a private view on the same three registered hulls. Stat-only entry points retain existing colours.

`ShipVariant.applyColor` lets the native hit/heal/selection mix run and then multiplies its draw tint by the selected Hull colour. Body and weapon texture shading remains intact. `cellColor` uses the chosen Accents with the native health-based darkening/pulse. Engine colour, bright inner colour and trail colour are private view fields; shared UnitEngine/Weapon objects, vanilla types, team colours and team indicators are unchanged. HUD/database icons are intentionally vanilla. There are no per-palette textures, shaders or registered types.

The center editor uses native Arc TextField/Slider/Table controls, a colour swatch and HSV gradients drawn with native quads. Valid HEX and HSV changes immediately update the draft and both previews. Invalid HEX retains the last valid draft and blocks Apply until corrected or the channel is switched/reset. Default colour resets the selected channel; Reset draft resets stats and all channels. Both are drafts until Apply. Closing discards them. The small center preview makes colour changes visible while editing, and the larger preview stays below the panels.

`ShipPreview` owns an unadded native unit and a cached private stat/cosmetic view. It draws only the outline, engine, body, cells and weapons under a UI transform, restoring draw state afterward. It never invokes world simulation or swaps the player’s unit/type for previewing. No GPU resources or shared sprites are modified. Private views refresh only when the draft changes.

Apply/reply use packet v4; authoritative state uses v3. The save chunk keeps its stable name and uses payload version 3, with readers for versions 1–3. New fields default to native colours for older chunks. Player colour preferences use `<UUID>.<tier>.colours` alongside the existing stat key in the same atomic properties-file replacement. Old profiles without that key retain default colours. Corrupt colour preferences fall back to native colours while valid stats restore. Current HP is preserved exactly when max HP does not change; a Durability change still preserves its fraction. Colours cannot bypass yard eligibility, ownership, tier, capacity or budget checks.
